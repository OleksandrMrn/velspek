---
name: implement
description: Implement an approved spec from docs/specs one session at a time, with scoped verification and self-review. Use only when invoked explicitly.
argument-hint: "<TICKET> [S<n> | T<n>] [what to fix]"
disable-model-invocation: true
---

Implement the approved spec of the ticket given with the invocation (`$ARGUMENTS`: `<TICKET>`, optionally one session `S<n>` or a single task `T<n>`, and, for a fixes run, what to fix), one session per run, the fixes run excepted (`docs/specs/README.md`, "Sessions").

1. Find the spec: the files `docs/specs/<TICKET>-*.md` whose front matter has exactly `ticket: <TICKET>` (`docs/specs/README.md`, "The spec file"); unless exactly one matches, stop and say so. Read `AGENTS.md` (sections 2.4 to 2.7, 3, 4 and 9), the spec and the ADRs it lists.
2. Check the status. Stop and say so unless it is `approved` or `implemented` (fixes after review; the approval stays in force, AGENTS.md section 2.3). A `draft` spec is approved by a person first.
3. Pick the work of this run. The state is what is on disk, also after an interrupted run: the ticks, "Log" and the working tree (AGENTS.md section 2.4); what an earlier run did not record is checked, not assumed.
   - Fixes named in the invocation or, on an `implemented` spec, by the review: the tasks the findings touch. This is the one exception to one session per run: the fixes may touch tasks of several sessions, since every session touched is checked again.
   - `T<n>`: that task; if it is ticked, a fix of it, and the invocation says what to fix. It runs whatever "Checked" the earlier sessions have; when one of them is not filled, the report (step 9) names the sessions that still wait for the person's check.
   - Otherwise a session: `S<n>` if given, else the first with an unticked task. A session runs only when every earlier session has "Checked" filled; otherwise stop and name the session that waits for the person's check. A session whose tasks are all ticked is a fixes run on it, and the invocation says what to fix. When no session is given and no task is unticked, the run finishes the spec: the whole verification (step 5), the self-review against all requirements (step 6) and the status (step 7).
   A ticked task that the run changes is unticked before the change and the "Checked" of its session cleared, so the person checks it again; it is ticked again when its fix has passed the scoped verification.
4. Execute the work: the unticked tasks of the session in order, the single task, or the fixes. Everything stays within the files the tasks name and the approved scope; minimal sufficient change; anything outside the spec goes into the report, not into the diff. A review finding that changes requirements, scope or approach is not implemented: it goes back to the spec, which is set to `draft` and approved again. A conflict with an accepted ADR stops the work and is reported (`docs/specs/README.md`, "ADRs"). Tick a task only when it is done and its scoped verification (step 5) has passed, the known baseline of AGENTS.md section 9 excepted. The next session is not started in this run, however much context is left.
5. After each task run the scoped verification of the spec (the commands of AGENTS.md section 9); after the last session, and in the run that finishes the spec, the whole "Verification". A failing check is understood first, not patched around.
6. When the session's tasks are ticked, and after a fixes run, do the self-review of AGENTS.md section 2.6 against the requirements its tasks map to and their checks; after the last session, and in the run that finishes the spec, against all requirements. A fix made in the self-review re-runs the checks it affects (AGENTS.md section 2.5).
7. Append the run to "Log" as one entry, `- [<YYYY-MM-DD>] <run>: <results>`, the run being `S<n> (T<a>–T<b>)`, `T<n>`, `fix after review (S<n>, T<n>)`, `fix after check (S<n>, T<n>)` or `finish`: what was verified and how, what was not and why, deviations and their reason, the finding each fix answers, out-of-scope findings. Set `status: implemented` only when every task is ticked and the whole verification has passed; the only failures allowed are the known baseline of AGENTS.md section 9, each named in the entry. Otherwise the spec is unfinished: an `approved` spec keeps its status; an `implemented` one (a fixes run that left a new failure, a check not run or a fix half done) is set to `approved` with the tasks unticked whose requirements the fix touches, so the approval stays and the spec shows what is open. In both cases name the tasks that remain, what fails or what was not run; a run that stops before its work is done also writes the unfinished action and the next command or check (AGENTS.md section 2.4).
8. Run `node docs/specs/_tools/check.mjs` and fix what it reports about this spec; if it cannot be run, say so.
9. No commits and no PRs. Report per AGENTS.md section 2.7, with the session's "Check" as what the person verifies next and a note that the next session starts with a new run once "Checked" is filled, then stop. Whether to commit between sessions is the person's call: do not ask. After the last session ask whether to commit and open a PR; either happens only on an explicit yes (AGENTS.md section 6).
